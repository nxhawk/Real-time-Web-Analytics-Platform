## What is being compared

PostgreSQL and ClickHouse over identical data, on the same machine, with the same memory
budget. The point is not to prove ClickHouse wins — it will, on these queries — but to
quantify by how much and to name the cases where it loses.

## Fairness rules

Skip any of these and the numbers are marketing rather than measurement:

- Same machine, same dataset, same memory allocation.
- PostgreSQL gets a fair schema: an equivalent table, an index on `(event_name, event_time)`,
  a BRIN index on `event_time`, and a second variant partitioned by month.
- `VACUUM ANALYZE` before measuring.
- Three runs, median reported.
- Cold and warm measured separately. Cold means dropping the OS page cache **and**
  ClickHouse's own caches.
- Disk footprint recorded — usually the most striking number of the set.

## Datasets

| Size | Events | Purpose |
|---|---|---|
| S | 1,000,000 | Smoke test, runs on a laptop |
| M | 10,000,000 | Differences become visible |
| L | 100,000,000 | The target scale, where the 300 ms requirement is verified |
| XL | 500,000,000 | Optional, needs a large disk |

Generated by `cmd/seeder` with a realistic distribution: Zipf over ~500 pages, devices split
62/35/3, top-10 countries plus a long tail, a 20:00–22:00 peak, weekends 30% lower. Conversion
and retention rates are configured up front so the funnel and retention queries can be checked
against a known answer.

## Conclusions to draw

Three questions the write-up must answer, in prose, using the numbers above:

**Why a column store is fast here.** Only the queried columns are read; sorted columnar data
compresses an order of magnitude better; execution is vectorised; a sparse index over sorted
data skips whole granules instead of walking a B-tree.

**Where ClickHouse is weak.** Point lookups by primary key, updates and deletes, large joins,
transactions. Say it plainly — a benchmark that only shows the winner is not credible.

**When to choose which.** A table, not a feeling.

## Recording the environment

Every result is meaningless without the machine it ran on. Record CPU, RAM, disk type, and
whether other services were competing for resources.

::: warning The production numbers are pessimistic
On the AWS deployment everything shares one `r7g.xlarge`: Kafka's JVM and the Go services
compete with ClickHouse for CPU and page cache. Numbers measured there are worse than a
dedicated host would give. State this next to the table — a reader who assumes a dedicated
box will draw the wrong conclusion.
:::
